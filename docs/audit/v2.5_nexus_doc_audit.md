# V2.5.0 Nexus Framework: Documentation Inaccuracy Report

This audit identifies obsolete architectural concepts, deprecated workflows, and critical omissions in the current EchoSync documentation suite based on the v2.5.0 rewrite.

---

## 1. Identified Inaccuracies (The "What is Wrong" List)

### `docs/APPLICATION_OVERVIEW.md`
*   **SyncID Obsolecence:**
    *   *Section:* 1. The EchoSyncTrack & SyncID Lifecycle (Lines 6, 20-28)
    *   *Inaccuracy:* Describes `SyncID` as the core "Fat Pointer URI" critical to ingestion and ghost track evaluation.
    *   *Reality:* SyncID logic is largely obsolete. The database has been decoupled, and provisional tracks no longer rely on this strict identifier for ingestion.
*   **Event-Bus Claim Check Pattern:**
    *   *Section:* 8. Event Bus & Sync Service (Lines 13, 76-79)
    *   *Inaccuracy:* Describes the Event Bus as the "nervous system" relying on lightweight dictionary payloads (the Claim Check pattern) to broadcast state.
    *   *Reality:* The Nexus framework has migrated to a Capability-Based routing model. The global dict-based event bus is deprecated in favor of direct capability querying and routing.
*   **Working.db Staging Explanation:**
    *   *Section:* 3. Database Architecture (Line 38)
    *   *Inaccuracy:* Refers to `working.db` merely as "ephemeral tracking data" (job queues, review tasks, user ratings).
    *   *Reality:* Fails to document the new unified JSON `track_data` staging blob, which is now the primary mechanism for storing provisional and discovery track data within `working.db`.

### `docs/EVENT_BUS_EVENTS.md`
*   **Complete File Obsolescence:**
    *   *Section:* Entire File
    *   *Inaccuracy:* Details legacy string-based and channel-based event bus publishing and subscription mechanisms.
    *   *Reality:* The system now relies on capability-based routing via `PluginRegistry.get_plugins_with_capability()`. The central string-based event bus is a legacy artifact.

### `docs/implementation_plan.md`
*   **SyncID References:**
    *   *Section:* 3. SyncID & CJK Integration (Line 11)
    *   *Inaccuracy:* Highlights SyncID as a crucial integration point.
    *   *Reality:* The architecture has pivoted away from SyncID.

### `docs/Guide.md`
*   **Working.db Definitions:**
    *   *Section:* Data Directories (Lines 24, 29)
    *   *Inaccuracy:* Defines `working.db` purely as ephemeral state (retries, rate-limit tracking).
    *   *Reality:* Missing the explanation of the new JSON `track_data` staging blobs that hold active discovery and staging state.

### `docs/SUGGESTION_ENGINE.md`
*   **Staging Queue Definition:**
    *   *Section:* Lifecycle Staging (Lines 110-112)
    *   *Inaccuracy:* Describes specific tables like `SuggestionStagingQueue`.
    *   *Reality:* The staging architecture now utilizes the unified JSON `track_data` blob in `working.db` rather than disparate queue tables.

## 2. Missing Concepts (The "What Needs to be Written" List)

The following core v2.5.0 features require dedicated explanation blocks across the documentation suite:

*   **Capability-Based Routing:** A complete explanation of how the Nexus Framework routes data and events by querying plugin capabilities (e.g., `Capability.FETCH_METADATA`) instead of relying on a global pub/sub Event Bus.
*   **The JSON `track_data` Blob:** Documentation on the schema, structure, and lifecycle of the JSON blob used inside `working.db` to stage track data, replacing old distinct table queues and strict relational enforcement.
*   **PluginBase Flexibility:** Explicit clarification that strict `@abstractmethod` inheritance on `PluginBase` has been removed. Plugins are now registered and evaluated based on exported classes and capabilities rather than strict OOP inheritance chains.
*   **`DEV_MODE` Toggle:** Documentation covering the `DEV_MODE=true` (or `ECHOSYNC_DEV_MODE=1`) environment variable, explaining how it bypasses aggressive plugin folder garbage collection and skips certain fast-path evaluations during local development.

## 3. Persona-Based Gap Analysis & Hallucination Risks

This section flags areas that will cause confusion or hallucinations for our four core user personas.

### A. Community Contributor
*   *Risk:* Contributors reading `APPLICATION_OVERVIEW.md` or `EVENT_BUS_EVENTS.md` will attempt to write new features using the old `EventBus.publish()` pattern instead of the new Capability-Based routing.
*   *Risk:* They will attempt to enforce strict `SyncID` validation during ingestion, leading to PR rejections.
*   *Gap:* Needs a clear migration guide detailing how to use `PluginRegistry` capability routing instead of the Event Bus.

### B. Community Plugin Developer
*   *Risk:* Will over-engineer their plugins trying to implement strict `@abstractmethod` overrides on `PluginBase` because the legacy documentation implies strict OOP enforcement.
*   *Risk:* Without knowledge of `DEV_MODE=true`, plugin developers will experience frustrating local development cycles where the system aggressively garbage-collects their active working directories.
*   *Gap:* The `PLUGIN_SDK_GUIDE.md` must be updated to remove any implication of strict abstract enforcement and must prominently feature the `DEV_MODE` environment variable.

### C. End User
*   *Risk:* Users reading `Guide.md` might attempt to manually clear or manipulate `working.db` believing it is purely "ephemeral retries," inadvertently destroying vital JSON `track_data` blobs needed for their discovery queues.
*   *Gap:* `Guide.md` needs to clearly define the new role of `working.db` as the holder of staging blobs, warning against manual manipulation.

### D. AI Agents
*   *Risk:* Context Window Pollution. `EVENT_BUS_EVENTS.md` and the SyncID sections in `APPLICATION_OVERVIEW.md` provide highly dense, structurally invalid architectural constraints. An AI agent will ingest these constraints and confidently hallucinate legacy code (e.g., generating `SyncID` parsing logic or `EventBus` subscription handlers).
*   *Risk:* When asked to create a plugin, an AI agent will generate rigid `@abstractmethod` boilerplate and fail to utilize capability enums, resulting in non-functional v2.5.0 plugins.
*   *Gap:* Documentation must be pruned of legacy concepts entirely. AI Agents require token-efficient, high-density explanations of the *current* state: Capability Enums, `track_data` JSON schemas, and relaxed PluginBase requirements.
